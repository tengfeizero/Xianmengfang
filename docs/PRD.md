# PRD — 现梦坊（codename: xianmengfang）

> 状态：v0.2，项目名与技术栈已定稿，其余待定项见第 9 节。
> 命名含义：现梦坊 —— 让创意（梦）走进现实（现）。
> 模式定位：单厂部署（一套系统服务一个工厂），架构预留多租户扩展空间。

---

## 1. 一句话定义

用户在小程序里创作作品（AI 生成 / 照片转风格 / 元素拼装），把作品图案应用到工厂商品（服饰/周边/玩偶）上，下单购买；工厂在 Web 后台接单生产、发货。

## 2. 角色与端

| 角色 | 端 | 主要操作 |
|---|---|---|
| 消费者 | 微信小程序 | 登录、创作、管理作品库、管理收货地址、选商品、下单、支付（MVP 为模拟支付）、确认收货、查看订单 |
| 工厂管理员 | Web 网页后台 | 管理商品（分类/规格/价格，后台可配置）、管理元素素材库、处理订单（接单/发货/填单号）、管理用户、查看 AI 用量 |

## 3. 消费者核心流程（MVP 最小闭环）

```
登录 → 进入创作工坊 → 三种创作方式任选 → 保存作品 → 选商品 → 选作品图案 → 下单 → 支付(模拟) → 管理员接单/发货 → 用户确认收货
```

### 3.1 创作工坊（三种方式）

1. **元素拼装**：预设底板（小姑娘/小男孩/小兔子/小熊猫）+ 分类元素（头发/帽子/睫毛/表情/服装/配饰），固定槽位换装 + 可微调位置缩放，最终合成为一张作品图。
2. **文字生成图**：输入描述 → 调 AI 生图 API → 生成插画作品。
3. **照片转风格**：上传手机拍摄照片 → AI 转指定风格插画作品。

### 3.2 商品与下单

- 商品：服饰类、周边类、玩偶类；分类、规格（尺码/颜色等）、价格、库存均由后台配置。
- 下单 = 选收货地址 + 选商品 SKU + 绑定一个作品图案 + 数量；也支持先加入购物车凑一单结算（见 3.2.2）。
- **收货地址（v0.6 新增）**：用户在小程序内自助管理收货地址（增/删/改/设默认，默认地址唯一，上限 20 条）；下单必选地址，收货人/电话/地址以**快照**形式写入订单——之后改地址不影响历史订单，工厂发货以订单快照为准。
- **支付：MVP 用模拟支付**（原因见第 6 节资质约束），下单即到"待发货"；真实微信支付待资质齐备后替换，支付模块预留接口。

#### 3.2.1 商品信息字段规划

v0.8 之前 `products` 只有分类 / 标题 / 描述 / images / 上下架 5 个字段，后台弹窗只有 3 个输入框、没有图片上传入口，演示数据 `images` 全是 `[]`——小程序商品页实际是"一张空封面 + 一句 20 字描述 + 规格标签"。定制商品与现货不同：用户看不到材质、尺码、可印区域、生产周期就不敢下单，出了问题也没有免责依据。字段分三批落地，每批独立可验收。

**P0 —— 让商品页先有内容可看（v0.9）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `subtitle` | string(128) | 卖点副标题，列表第二行；现在用 `description` 顶替，语义混在一起 |
| `images` | JSON 数组 | 商品主图，建议 5 张（正面/背面/细节/场景/尺寸）。字段早已存在，缺的是后台上传入口和真实数据 |
| `original_price_cents` | int（分） | 划线价/参考价，0 表示不展示；只用于表达优惠，不参与结算 |
| `unit` | string(8) | 计价单位（件/个/套），默认「件」；数量框旁显示「共 N 件」 |
| `detail` | text | 文字详情，按空行分段渲染：材质、工艺、尺码表、注意事项 |
| `detail_images` | JSON 数组 | 详情长图，纵向拼接。工厂拍几张图比写文案快，这是主力 |
| `service_notes` | string(255) | 服务承诺 + 售后例外，如「48 小时内发货 · 定制商品不支持七天无理由退货」 |
| `sort` | int | 排序权重，大的靠前；同权重按 id。现在只能按 id 排，新品永远排最后 |

> 划线价放 SPU 而不是 SKU：当前每款只有 1–3 个规格且同价，用 SPU 表达"原价 129，99 起"够用。等出现同款不同规格差价明显（如加绒款）再下沉到 SKU，已在 P1 备注。

**P1 —— 结构化属性与运营字段**

| 字段 | 说明 |
|---|---|
| `attrs` | 属性组 JSON（材质/尺寸/重量/工艺/产地/洗涤说明），详情页渲染成参数表。比全堆进 `detail` 更利于后台复用和后续筛选 |
| `skus.image_url` | SKU 图，换色换图。现在点规格标签只有价格变，图不变 |
| `tags` | 标签 JSON（新品/热销/包邮/定制），列表角标 |
| `min_qty` / `max_qty` | 起订量与限购。定制玩偶常有 2 件起，秒杀类需要限购 |
| `lead_time_days` | 生产周期（工作日），详情页展示「预计 X 个工作日内发出」——定制单最容易被追问的就是"什么时候发" |
| `share_cover` | 分享封面（5:4），小程序转发卡片用，不然转发出去是随机商品图 |

**P2 —— 交易与内容增强**

| 能力 | 说明 |
|---|---|
| 运费模板 | 当前全店包邮（`amounts.shipping_cents` 恒为 0）。要做「满 X 包邮 / 按重量 / 按地区」需要独立 `freight_templates` 表，牵动下单金额计算 |
| 评价体系 | 订单完成后评价，商品页展示评分与晒图；涉及新表、图片审核与刷评风控 |
| 销量展示 | 真实销量或展示销量。每次列表 count 订单太重，需冗余字段 + 定时汇总 |
| 商品视频 | 主图位第一帧视频，小程序 `video` 组件 |
| 富文本编辑器 | `detail` 从分段纯文本升级为富文本。后台体积明显变大，等真有运营人员维护内容再说 |

**明确不做**：多仓、预售、组合商品、SKU 级库存预警。单厂单仓 + 定制生产，加了没人维护，反而增加后台认知负担。

**合规要点**：定制商品属于《消法》第 25 条"消费者定作的商品"，不适用七天无理由退货，但**必须在下单前明确告知**，否则平台仍判商家承担。因此 `service_notes` 在下单页固定展示一条不可关闭的提示，不依赖商家自己填。

#### 3.2.2 购物车（v1.0 新增）

v0.9 之前下单路径是"商品页 → 立即购买"，一次只能买一个 SKU；用户想配齐 T 恤 + 马克杯 + 玩偶就要下三单，工厂也要发三个包裹。购物车把"凑齐一次买"补上。

**决策（已确认 2026-11-06）**

| 决策点 | 结论 | 理由 |
|---|---|---|
| 入口 | tabBar 第 5 个「购物车」 | 电商高频入口，一步可达；现 4 项 + 1 = 5，未超微信上限 |
| 存储 | 服务端 `cart_items` 表 | 换设备/重装不丢；加购与结算都能校验库存/下架，与订单口径一致 |
| 结算 | 勾选部分结算 | 想先买一件不必删掉其他商品；支持全选/全不选 |
| 作品绑定 | 每项可单独绑一件作品 | 同一 SKU 配不同图案 = 不同购物车项；下单时每项带自己的 work_id，与订单明细结构一致 |

**核心规则**

- 购物车项唯一键：`user_id + sku_id + work_id`（work_id 空按 0 处理）。同款同图重复加购 = 数量累加，单件数量上限 99；购物车条数上限 50。
- 加购时校验：SKU 存在、商品上架、库存 ≥ 1（不锁库存，结算时原子扣减，缺货在结算时报错——与直接下单同一口径）。
- 列表每项返回实时状态：商品名/封面/规格/单价、绑定作品缩略图、当前库存、**是否失效**（商品下架或 SKU 删除标灰，不可勾选结算，可删除）。
- 结算：勾选项 + 收货地址 → 复用现有 `OrderService.Create` 生成**一单多明细**订单（mock 支付直达待接单）；订单创建成功后移除对应购物车项。删除失败仅残留（用户可手动删），不影响订单正确性。
- 金额口径与订单一致：全部按 SKU 现价结算，购物车里显示的价格只是参考，以结算时为准；全店仍包邮。

**边界（明确不做）**：跨店/多仓概念、优惠券与凑单推荐、购物车备注、结算页（勾选项直接按默认地址下单，地址在购物车页选择）。失效项不自动清理，由用户手动删。

### 3.3 订单状态机

```
待支付(模拟支付则跳过) → 待接单 → 待发货 → 已发货 → 已完成(确认收货)
                      ↘ 已取消
```

## 4. 管理后台（Web）

- 登录（管理员账号密码，密钥/密码不写死在代码里）
- 商品管理：分类、SPU/SKU、价格、库存、上下架
- 素材管理：拼装元素上传（分类、PNG 图层素材）、底板管理
- 订单管理：列表/详情、接单、发货（填物流单号）、退款标记（MVP 仅标记，不做退款流）
- 作品审核（可选开关）：管理员可下架违规作品【待定：MVP 是否需要】
- AI 用量看板：调用次数、费用估算

## 5. 技术方案（已定稿 2026-11-06）

- **后端**：Go（Gin + GORM），数据库 SQLite 起步，后期迁 PostgreSQL；MQ/Redis/ES 等暂不引入，按需再说。
- **前端**：微信小程序（原生）+ Web 管理后台（Vue 3 + TS + Element Plus）。
- **部署**：待采购云服务器（Linux）+ 域名 ICP 备案；小程序要求 HTTPS + 备案域名。
- **AI 生图**：先接低价/免费额度国内 API，生图能力封装为独立 service，换厂商不动业务代码；密钥只走环境变量。

## 6. 资质与合规约束（重要，你需要提前准备）

1. **你目前是个人主体小程序**：个人主体不能开通微信支付，也不适合电商类目。MVP 用模拟支付开发；上线收款前需要注册个体户/企业主体小程序 + 微信支付商户号。
2. **服务器 + 域名**：需购买云服务器与域名并完成 ICP 备案（小程序要求 HTTPS + 备案域名），备案约 1-2 周，建议现在就启动。
3. **AI 生图密钥**：由你注册并付费，密钥只进服务器环境变量，绝不进代码仓库。
4. 内容安全：用户上传照片与生成作品需过微信内容安全校验（msgSecCheck/imgSecCheck）。

## 7. MVP 边界（明确不做）

- 真实微信支付（资质齐备后做）
- 多租户/SaaS 化（仅架构预留）
- 退款/售后流程、物流跟踪详情、评价体系
- 元素自由拖拽拼贴（仅做固定槽位 + 微调）

## 8. 验收口径（最小闭环）

一条链路可演示：新用户登录 → 拼装一个作品 → 选一件商品绑定该作品 → 下单 → 后台接单发货 → 用户确认收货，订单状态流转与数据全部正确。
